## 1. Music cluster (intro never stops / no slideshow track / no change at stage start)

The shipped game keeps the CD track it selected in DS, written by `fn_010b1d` (`0x010bfc`-`0x010c26`):
`DAT_00053c44` = start LBA, `DAT_00053c40` = end LBA, `DAT_00053c48` = length in seconds. So the shipped
side's music schedule is readable from memory, and the port's is witnessed directly
(`rig_cdda_marker`: play/stop with index/LBA/sectors, `port/cdda.jsonl`). `scripts/rig/ds_trace.py`
prints both per phase.

Combat route (`report_state` + `ds_trace 0x53c44,0x53c48`), values are LBAs:

| window | shipped | port |
|---|---|---|
| P0@47200 (title up) | 0x2d320 (track 9, len 0x171 s) | 0x918e → 0x2d320 (track 1 → 9) |
| P1@49300 (stage data) | 0x367aa (track 11, len 0xee s) | 0x2d320 → 0x367aa |
| P6@70000 (slide stepping) | **0x367aa still** | **0x9ddf (track 2, len 0x105 s)** |
| P7@72000 | 0x9ddf | 0x9ddf |

Divergence: the port selects the room track (LBA 0x9ddf = disc track 2) at t=70.75 s, ~2 s before the
shipped game does, *while the slides are still running*; and the port's stop marker
(`cdda.jsonl` `{"t_ms":70750,"event":"stop"}` then `play index 2` at 70751) shows the previous track is
torn down at that instant, whereas the shipped side keeps track 11 selected across the whole slide
window. Suspect region: the room→track table `g_tab_52da4` indexing in `cd_track_for_room` and the slide
loop's call of `fn_10b1d` — i.e. the port asks for the room track too early and never plays a slideshow
track at all (no play mark between 50.2 s and 70.75 s in `cd-port`/`cd-port2` other than track 11).

yet observable (no DS cell, and `/api/v1/io/port` sampling of the MSCU/DSP ports is not wired into the rig
yet — see §4).

## 2. EXP / kill quota — the first signal was a rig defect, now corrected

The first pass reported `0x52a1c` differing in every window (shipped `0x3e8` = 1000, port `0xe8` = 232).
That was wrong, and the gate is what exposed it: the generated cell table gave `g_tab_52a1c` a **host size
of 1 byte**, because the port declares it as `uint32_t g_tab_52a1c[0x4ec/4]` and the dimension parser
could not evaluate `0x4ec/4`, so it silently fell back to one element (`max(1, elems*slot)`).
Comparing one byte of the port against four of the guest is exactly the 232-vs-1000 truncation the
numbers suggested. `scripts/audit/port_src.py` now evaluates array dimensions arithmetically
(`eval_dim`, returning "unknown" rather than 1 when the dimension is not a plain integer expression);
three cells changed size (`0x5274c`, `0x52a1c`, `0x5d884`: 1 B → 256 B) and after re-dumping the port,
`0x52a1c` no longer diverges at all.

The image at DS `0x52a1c` (file `0x4b41c`) is `0x3e8` repeated — the port's `kTab52a1c_init` + `memcpy`
copy is faithful. So the "no EXP on kill" item has **no state-oracle signature yet**: the quota table is
correct, which moves the suspicion to the award path (`fn_25343`'s kill/quota block) or to the per-kill
counter, neither of which the route made diverge. Recorded as a rig gap: the EXP award needs a dedicated
drive that lands a kill (the combat route punched a lot but never killed), not a change to the port.

## 4. Combat state machine (hurt/stagger, infinite punching, fallen, stuck-while-kicking)

Two DS cells that name the machinery directly:

- `0x62d58` — "the state id of the action currently being chained". Shipped stays `0x0` through the whole
  fight window; the port reaches `0x33` and holds it (P18-P20). A chained action that never clears is the
  infinite-punching symptom's shape.
- `0x6339c` — "forced-transition countdown (500 → state 0x28)". In the fight window the shipped side's
  samples stay `0x0` while the port's arming values run `0x21, 0x6, 0x83, 0x7f, 0x1, 0x4, 0x3, 0x5`
  across P7-P16. The countdown that is supposed to carry a hit into a stagger state is therefore armed on
  one side and behaves differently on the other.

Entity/resource records: the rig dumps 64 bytes at every pointer cell on both sides
(`scripts/rig/record_diff.py`). Over the fight window (62-160 s, 21 phases) the blocks at
`0x63dd4 0x63e00 0x63e0c 0x639c0 0x639ec 0x63350 0x6334c 0x62ac4` differ in *all* 50 sampled blocks, at
offsets `+0x00 +0x04 +0x05 +0x06` (shipped `0x0a/0x34/0xd8/0x28` vs port `0x80/0x80/0x80/0x80`).
Those cells are not entity records: the port's own names say they are resource blocks — `dust.spr`
(0x63dd4), `gage.spr` (0x63e00), `pause.spr` (0x63e0c), `system.spr` (0x639c0), `catch4.key` (0x62ac4),
allocated by `spr_block()` (f.c:2448) — and there is no such file in `NIGHT/`, so the shipped game builds
them at runtime. The port's copies are still allocator-poison (`0x80`) in every combat window: **the port
allocates these blocks and never fills them.** The static audit already marks the pair as `PTR` ("host
slot 8 B vs guest 4 B", the docs/94 offset-vs-pointer family), and this is that family confirmed at
runtime. `0x639ec`/`0x63350`/`0x6334c` are pointer *arrays* (256 B cells) and are now excluded from the
record histogram rather than dumped as if they were records. **Rig gap, next step:** until the record dump resolves the port's representation and
the guest's DOS-flat representation into one common layout, the fallen-reachability and teleport
(position continuity) fields cannot be read; they are the two items this gate could not localize to a
field, and the fix is in the rig (`rig_sink` record resolution + a decoded field table), not in the game.

## 6. Second gate pass: kill drive, symbol-mapping fixes, and what the records actually say

`scripts/rig/drives/ep1_kill.txt` (same two anchors, then 72 s of alternating punch `ctrl` / kick `alt`
with distance-closing nudges), output `/tmp/rig/route-k2`.

Two rig defects surfaced before any behavioural conclusion could be drawn, both in the symbol map that
feeds both the static audit and the state oracle (`scripts/audit/port_src.py`):

1. **Type filter dropped the entity globals.** `uintptr_t` / `intptr_t` / `size_t` were not in
   `TYPE_SIZE`, so every declaration using them was skipped outright -- including `uintptr_t g_dat_53c84`
   (the guest's "second entity slot"). With them added the symbol table grows 514 → 574 declarations.
2. **The address marker was being read from the wrong place.** Statements are segmented at top-level `;`,
   but the port writes `uint8_t *g_player_ent = 0;      /* 0x53c7c ... */`, i.e. its own marker *after*
   its own `;`. Comment bodies also contain `;`, which split statements into comment fragments.
   `port_src._statements` now skips comment bodies and yields offsets, and the marker is taken from the
   statement's tail plus a comment that starts on the same physical line as its `;`. Result: 415 → 491
   mapped globals, 246 → 279 rig cells (0x53c7c player entity, 0x53c80 latched entity, 0x53c84, 0x53c88
   now dumped on both sides), and zero disagreements between name-derived and comment-derived addresses.

`gen_headers.py` also stopped picking the wrong owner of a cell: `g_dat_53c7c_null_warned` (a port-local
debug flag that merely *looks* like DAT_00053c7c) was sorted ahead of `g_player_ent` alphabetically and
replaced the player-entity pointer in the rig table. Selection is now by shape (pointer/widest first) and
every contested cell is written to `scripts/audit/gen/port_dup_claims.json`; five cells are claimed by
*different* port names -- `0x537ca`, `0x53c7c`, `0x53d0c` (`g_pool_53d0c` uint32_t[100] vs
`g_dat_53d0c` uint8_t*, the docs/98 SFX pool), `0x5d0b4`, `0x63f90`. Two of those sit exactly on the
items the playtest reports.

Kill/EXP measurement (`ds_trace 0x639bc` = the room kill counter that feeds the quota,
`0x53c68`, `0x6336c` = the stage-event request):

```
phase          0x639bc (orig | port->/mode)      0x53c68
P80@102000     0x0 / 0x1                         0x0 / 0x2
P112@114800    0x0|0x1->0x2 / 0x1                0x0|0x1->0x2 / 0x2
```

The port registers its first kill at ~102 s, the shipped game at ~114.8 s: both sides count kills, so the
playtest's "no EXP on kill" is **not** a dead kill counter. It has to be downstream -- the per-kill score
`e[+0xbb]` folded into `player[+0x52]` and totalled into `player[+0x2b]` (f.c:24799) -- which needs the
entity record, and that is where the rig is blind:

```
cell g_player_ent ds=0x53c7c  rec 64B
P65@95900 .. P96@108400   +0x17 0/80   +0x2b 0/80808080   +0x30 0/80   +0x1 0/80808080
REC-NULL: orig block all zero, port block allocator-poison (0x80)
```

Across all 572 shipped-side samples DS `0x53c7c/0x53c80/0x53c84/0x53c88` read 0 while the port holds live
pointers there, and the *cell* `0x53c68` reads 0 on the shipped side but 1-6 on the port. Ghidra says both
cells are written (`0x53c7c` WRITE at `0x0003b01b` in `fn_03af18`; `0x53c68` READ_WRITE at `0x000111be`
`fn_010efc` and `0x000113d0` `fn_0112fd`), so "zero in DS" cannot be the steady state of a live room.
The shipped-side DS read itself is trustworthy (the exptab costs `0x12c/0x3e8/0xfa0` at `0x53c94-0x53c9c`
and the resource pointers at `0x53c64/0x53c8c` read correctly), which leaves the representation: these
cells hold **heap-relative values in the guest** while the port keeps host pointers, and the shipped-side
record reader passes the raw value to the memory API as a physical address. That is the docs/94 family
again, and until the shipped-side reader resolves heap-relative pointers the entity-level items
(EXP-per-kill, fallen reachability, teleport position continuity) stay undetected. Recorded as the rig's
next defect, not as a port finding.

## 7. Third gate pass: the port's record dump was broken, and what the records then showed

Before any entity conclusion could be trusted, the port-side dump had to be fixed. `app/rig_sink.c`
laid out the cell area (`g_off`) but **never assigned `g_recoff`**, and set `g_rec_bytes` to the cell
area only -- so the `if (g_recoff[i] != 0xffffffffu)` test passed with offset 0 for *every* pointer
cell and each pointer's object was memcpy'd over the first cell's bytes. `meta.json` said
`rec_offset: 0` for all 43 pointer cells. Every `REC-*` row in every earlier report was therefore
comparing the wrong bytes. Fixed: record blocks are now allocated after the cell area
(`record_bytes` 6169 -> 25860 for this table), `rec_offset` distinct per cell
(`0x53c70`@11780, `0x53c74`@12132, `0x53c7c`@12836), and every reader
(`diff_state.py`, `record_diff.py`, `ent_fields.py`) takes block size/offset from the dumps instead of
a hardcoded `RB = 64`. Both sides now dump `0x160` bytes per pointer target.

Route `ep1_combat` again, port re-dumped with the fixed binary: `/tmp/rig/route-e1`
(655 shipped samples, 51 pointer cells, 749 port samples in the combat window).

Also corrected here: a misreading in section 6. In the `ds_trace` column format
`orig_mode | port_transition / port_mode`, the `0x0|0x0->0x1/0x1` at P48@171390 is the **port**
incrementing the room kill counter `0x639bc`; the shipped side stayed at 0 in all three drives
(k1, k2, e1). And in k1/k2 the shipped side never reached combat at all: across 583 and 572 shipped
samples `0x53c68` (entity count), `0x53c70` (list head), `0x53c74` (tail) and `0x53c7c` (player entity)
were all zero, while `ep1_combat` gives count 3-4 and live pointers in 600+ samples. Those drives were
missing `anchor static` and the slide-stepping `enter` keys, so the shipped game sat on the title
slides. Any entity comparison on k1/k2 was vacuous -- the rig's own drive was the defect.
