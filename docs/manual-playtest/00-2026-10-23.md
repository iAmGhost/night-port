# Issues found by manual playtest

Status legend: `[x]` root-caused, fixed and measured; `[ ]` still open. Each entry names the root cause, the
analysis document, and the evidence a reviewer can re-run. Reproduce a scripted run with

```
cd port && SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy ./test/night \
    --script ../scripts/playtest/arrows_crash_hunt.txt --shots /tmp/ch --frames 9000
```

(`scripts/playtest/route_episode1_anchored.txt` is the shorter episode-1 route; `wait res NAME` anchors keep
the key timing identical whatever the host speed or audio state -- docs/56.)

- [x] No company logo shown at game launch(before playing intro video) — FIXED: the 0x3DA retrace wait was
  stubbed, so the logo screen existed but was never held (docs/47). Evidence: `01-shots/0000_logo.pcx.bmp`,
  manifest first row `logo.pcx`. A second, independent bug hid it: the logo is drawn through 64 KB VESA
  windows, and `fn_03628e`'s window slide was a no-op, so only part of the plate was ever visible (docs/51);
  after the fix the whole 0x4b000-byte still lands in order and the frame shows the same meteor streak and
  "ENTERTAINMENT" wordmark as the asset (`02-shots/03-logo_asset_vs_port.png`); row-mean brightness reaches
  0.88 of `logo.pcx` at the fade plateau (~800-900 ms) -- the screen fades in and out, so a raw pixel threshold
  has to be taken at that plateau (docs/51 table). Regression pins: `test_fn_03628e` absolute window indices
  (0, 0xa000, 0x10000, 0x3b000, 0x4afff).
- [x] Intro video screen artifact: see 00-screenshots/broken_intro.png — FIXED: the Autodesk .fli player
  (`fn_03f6bc`) works on a 320x200, 320-pitch, 64000-byte frame, but the host's read-back used the current
  640-pitch 307200-byte screen, so every presented frame was sheared (docs/53, docs/54). The view flag
  `g_view_320x200` now brackets the player call. Evidence: 88/88 frame snapshots byte-identical to the
  ffmpeg decode of the same `opening.fli`, and port shots vs ffmpeg reference at matched frame indices
  (#39/#57/#68/#98) with mean L1 1.45-2.00 -- the floor that two identical images produce;
  `02-shots/05-fli_port_vs_ffmpeg.png`. Regression pins: the `fn_03fb73` packet-chain test plus the
  view-flag instrumentation (320x200 inside the player, caller's value restored on return).
- [x] Main title animation(melting-like effect) plays too fast — same root cause (docs/47): fade/animation
  frames are paced by the retrace wait. Evidence: `01-shots/0021_title1.pcx.bmp`, 621 retrace waits measured
  by t=33s.
- [x] No introduction slideshows shown before episode start(skips entirely to main game) — same root cause
  (docs/47): the slide cards are shown with retrace-paced fades. Evidence: `01-shots/0023_1s1.pcx.bmp`,
  `0025_1s3.pcx.bmp` (1s1 -> 1s2 -> 1s3 then stage1.pcx), and in the anchored manifest rows
  `1s1.pcx`, `1s2.pcx`, `1s3.pcx`, `stage1.pcx` in that order.
- [ ] While starting stage 1 screen is corrupted(it recovers after a while, see
  00-screenshots/stage_transition_artifact.png) — not reproduced by the scripted route so far, and measured
  rather than assumed (docs/54): the structural edge-noise (mean absolute difference against the four
  neighbour pixels) of the first gameplay frames is 29.6-30.2, against 58.6 for the sheared intro frames
  above, at the correct 320x200 view -- i.e. no garbage band or shear in any captured transition frame, in
  the earliest pre-fix run as well as now. What is still missing is coverage: the transition is sampled by 1-2
  automatic shots instead of every presented frame, so an in-flight composite/fade frame could still be wrong.
  Next step is a dense-capture window from the `stage1.pcx` hold to the first `stage_play` shot.
- [x] Enemy sprites are main character's sprite. also player is missing(00-screenshots/enemy_sprite_health_bar.png)
  — FIXED in code (docs/49): the per-type `.spr`/`.act` name arrays (`kTypeSprNames`, `kTypeActNames`) were
  shifted by one entry, because they hold pool offsets from DS 0x50000 rather than string pointers, so type 31
  loaded `gun.spr` instead of `ena-1.spr`. Evidence from the live game rather than a fixture
  (`03-shots/06-entities.txt`): in stage 1 the player block is present (`isPlayer=1`, world 97,139, facing
  set by the scripted arrow press) with `type(act)=0 type(spr)=0`, while the two enemies are
  `type(act)=31 type(spr)=31` -- i.e. their action container resolves to `g_dat_53818[31]` and their sprite
  struct to `g_dat_639ec[31]` = `ena-1.spr`/`ena-1.act`, which the suite pins directly (`test/test_f1.c`,
  "kind-1 record: ena-1.spr loaded as the type-31 sprite struct"). Original-frame side-by-side still pending
  (see the DOSBox capture note at the bottom).
- [x] Health bar position is wrong — FIXED from the code, not the screenshot (docs/50): two causes. (1) the
  frame pitch DAT_40010 was never set (its second port name g_video_stride was never assigned) so every
  pitch-relative write collapsed to row 0; (2) `rect_fill`'s argument pair was transposed in fn_01348f -- the
  push order at 0x13745-1375e/0x13771-0x13789 makes it rect_fill(base, COLUMN=slot*0xaa+0x17, ROW=0x1f, w, h,
  colour), so the gauge fill belongs at column 23, row 31 (inside the panel blitted at row 0x1d), while the
  port drew it at column 31, row 23. Measured after both fixes: the fill is exactly columns 23..122 on rows
  31..32, nothing on rows 27-30/33-37 (`02-shots/04-playing-hud-position-fixed.bmp`).
- [x] Broken sound: `2026-10-23 16:09:04.957 night[25293:71832293] audio device: CoreAudio error
  (AudioQueueStart): 2003329396` — FIXED (docs/55), and it took two independent causes.
  (1) Host half: the device is now chosen by a ladder -- system default, then every other playback device,
  then a drain-only null sink -- so a broken CoreAudio device can no longer abort boot or wedge the run
  (`sys_audio_plan()` in `src/sys/sys.c`, pinned by unit checks). The same CoreAudio fault had also been
  blocking dosbox-staging itself from running non-interactively; `SDL_AUDIODRIVER=dummy` is the workaround
  there. (2) Port half, the actual mute: `DAT_00053338`, the sound/music enable byte that gates `fn_04185e`,
  was initialized to 0 while the shipped image initializes it to 1 (byte at DS 0x53338), so no DSP command
  and no DMA transfer was ever programmed. Measured with the board modelled (`NIGHT_BOARD=1`) on the anchored
  route: `xfer=61 stops=63 pushed=220027 pend=0 snden=1 devinit=1 plays=63`, 8-bit PCM at 10989 Hz (the DSP
  0x40 time constant), ring fully drained; with a host stream attached `submitted=11310 B` of that reaches
  SDL inside the latency bound. One shipped `.voc` slot driven on its own (`NIGHT_PLAYVOC=7`) moves the
  counters by exactly one asset: 61 -> 62 transfers, 5233 bytes.
  Still open for this item: Red Book CDDA -- only MSCDEX *stop audio* is modelled in the sys layer.
- [x] Pressing arrow makes game crash: `zsh: segmentation fault  ./test/night` — FIXED (docs/55):
  `fn_034635` read the player entity pointer `DAT_00063c7c + 0x1b` on a key make; that pointer is only valid
  once a stage is loaded, so a key press on the logo/intro/title/menu screens read DOS heap offset 0 on the
  original (mapped, garbage, inert) and faults on the host. The read is now skipped with a one-time report --
  same inert outcome, no crash -- and pinned by unit checks. Reproduced against the reported symptom with a
  dedicated route, `scripts/playtest/arrows_crash_hunt.txt`: 34 arrow/Ctrl presses spread over logo, intro
  film, title card, slide cards and stage play, exit code 0, no fault, and the run still reaches
  `stage_play`/`playing` with 3 entities (`03-shots/06-arrows-crash-hunt_*.bmp`).

## Still open, in priority order

1. Red Book CDDA play path in the sys layer (`fn_10b1d` has no host backing; only stop is modelled).
2. Dense per-frame capture across the stage transition, to close or confirm item 5.
3. Original-side frames for the comparisons that need them (pause/level-up/game-over, stage transitions).
   The recipe is in docs/46: dosbox-staging needs `SDL_AUDIODRIVER=dummy` to run non-interactively, `mount d
   <cue> -t iso`, and `exit` in `[autoexec]` (a `SIGKILL` truncates the guest's files). The guest-side snapper
   (`scratch/snapsr/snap.asm`) currently writes a correct header+DAC record but an empty framebuffer record;
   the diagnosis and the next experiment are written up at the end of docs/46. Host-side key injection does
   not work from this session: System Events reports `frontmost=false, count of windows=0` for
   dosbox-staging, so neither AppleScript nor `cliclick` has a target window.
