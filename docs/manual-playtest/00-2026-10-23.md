- [x] Broken sound: `2026-10-23 16:09:04.957 night[25293:71832293] audio device: CoreAudio error
  (AudioQueueStart): 2003329396` — FIXED (docs/55), and it took two independent causes.
  (1) Host half: the device is now chosen by a ladder -- system default, then every other playback device,
  then a drain-only null sink -- so a broken CoreAudio device can no longer abort boot or wedge the run
  (`sys_audio_plan()` in `src/sys/sys.c`, pinned by unit checks). The same CoreAudio fault had also been
  blocking dosbox-staging itself from running non-interactively; `SDL_AUDIODRIVER=dummy` is the workaround
  there. (2) Port half, the actual mute: `DAT_00053338`, the sound/music enable byte that gates `fn_04185e`,
  was initialized to 0 while the shipped image initializes it to 1 (byte at DS 0x53338), so no DSP command
  and no DMA transfer was ever programmed. Measured with the board modelled (`NIGHT_BOARD=1`) on the anchored
  route: `xfer=61 stops=63 pushed=220027 pend=0 snden=1 devinit=1 plays=63`, 8-bit PCM at 10989 Hz (the DSP
  0x40 time constant), ring fully drained; with a host stream attached `submitted=11310 B` of that reaches
  SDL inside the latency bound. One shipped `.voc` slot driven on its own (`NIGHT_PLAYVOC=7`) moves the
  counters by exactly one asset: 61 -> 62 transfers, 5233 bytes.
  (3) A third bug sat underneath both: **no SDL3 stream was ever bound to the opened device**
  (`SDL_BindAudioStream` was missing), so the board's bytes were accepted by the stream -- the counters
  happily grew -- but never reached hardware; the backlog climbed to ~98 KB and stopped at the latency
  bound. After the bind: `submitted=261902 B` with `stream=0 B`.
  (4) Red Book CDDA implemented (docs/57): `fn_010b1d` was a no-op stub whose note was wrong twice -- it
  *is* given an argument (`0x010b35 MOV [EBP-4],EAX`) and it *is* the track-start request, resolving the
  track through the TOC record array and reading its sectors via the MSCDEX media read (request 0x1510).
  With the faithful port the route now selects four tracks (`track index 1 lba=37262 sectors=3153` --
  3153 is exactly the `0xc51` the disc-present gate `fn_010c3e` checks -- then 9, 11, 2 from the room
  table `g_tab_52da4`) and feeds **44 934 960 B** of CD-DA (12 320 sectors, ~164 s of 44.1 kHz stereo) into
  a second stream bound to the same device, mixed by SDL alongside the effects. Measured on the image:
  the audio sectors hold **little-endian** S16 PCM (per-channel lag-1 autocorrelation 0.982/0.972; the
  big-endian reading is uncorrelated), so no byte swap is needed.
  Honest limit: every physical device on this machine refuses with the same CoreAudio error
  (`default`, MPG321UX, Mac Studio, Teams, Jump Desktop -- `AudioQueueStart 2003329396`), which is a
  machine-level fault (it blocks dosbox-staging too). Under it the port now degrades correctly: log each
  refusal, fall back to the software sink, keep the game running and still consume the track at the
  disc's 75 sectors/s (`cdda=94080B ... 446880B`). With a working device there is no error at all
  (`audio: default at 48000 Hz`).
  Evidence file: `06-shots/audio_counters.txt` (the host pump counters from a scripted episode-1 run:
  DSP/DMA transfers and the CD-DA byte count both non-zero). Audio has no screenshot; the counters are its evidence.

## Closure of item 3, and a new defect found while chasing it

Item 3 (original-side frames) is now closed as a **measured dead end on this machine**, all five routes
recorded at the end of docs/46: `screencapture -x` is all-black even with a real Metal window present
(`DISPLAY: Using 1671x1253 window size in windowed mode`, `SDL: Using 'metal' SDL render driver`); System
Events reports `0` windows for the dosbox-staging process; 0.83 has no shell-internal capture command
(`capture`, `capture video`, `capture image` all print `Illegal command: capture`, read back by redirecting an
internal command to a file); there is no file-backed LPT/serial device (only LPT DACs); and the in-guest TSR
(`scripts/rig/snapper/snap4.asm`) proved that writes land from the install context (`S4LOG.BIN` 16 B,
`S4VID.BIN` 2048 B) while its INT 1Ch handler produced **zero** records over 70 s of the real game -- NIGHT
takes the timer through its protected-mode IDT, so the real-mode timer chain never runs in-game. The two
probe defects that had made this ambiguous are fixed in snap4: `mov ax,0x4202` followed by `mov bx,ax` handed
the function number to DOS as the file handle, and an earlier cleanup had removed the create call so `open`
failed without a trace.

The comparisons that needed the original's frames are instead made against the shipped asset decoded
independently, and that basis is stated wherever it is used (docs/63; the slide cards in docs/62 are the
worked example: every intro slide of the six episodes that ship them is 307200/307200 bytes identical to its
card in the screen arena).

**New defect, filed:** the game-over / CONTINUE screen crashes. `NIGHT_SHOWSCREEN=gameover` invokes the
shipped `fn_038445` and it segfaults in the first `fn_03bb42` composite (`0x00038554-0x000385ce`). The
diagnostics show every precondition is fine (digit block and the three `gameove<N>.pcx` buffers allocated,
`over.spr` loaded, all sub-table offsets inside the 0x3000000 arena) and that the value read as `p4[i+1]` is
count-like (`0x4e 0x48 0x46 0x14 0xf 0x35`) rather than address-like -- a mis-read `.spr` struct field, the
same convention family as the font `+0x34/+0x38` and room-chain fixes. The disassembly of that range is the
next step; it is recorded in docs/61 with the evidence rather than guessed at.

### 10. Game-over / CONTINUE screen crashed the process -- FIXED
Symptom: `NIGHT_SHOWSCREEN=gameover` (host warp into the shipped `fn_038445`) died with SIGSEGV.
Root cause (capstone over `0x00038554-0x00038601`): two transcription errors repeated at all four
