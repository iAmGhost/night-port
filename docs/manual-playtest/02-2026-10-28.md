# Still broken things

Do not rely on replication, do deep analysis from decompiled code for accurate port.

Status legend: `[x]` = root-caused from the shipped binary, fixed, and re-measured by the differential rig
(docs/150 is the per-item ledger; docs/151 is how the rig stands as the verification basis). Items that are
not closed stay `[ ]` with the exact measurement that is missing.

- [x] Music is still broken. **(UNSOLVED at the time of writing — resolved by the rig, see below.)** Intro
      music never stops even title appears. Does not play music for slideshow. Does not change music when game
      starts.
      * ROOT CAUSE: three separate things were folded into one report. (a) `cdda_play` reused one SDL stream
        without flushing/stopping, so the previous track bled across every selection — the "never stops"
        symptom. (b) the *extra* selection (a 12th track at 236.5 s) was not a CD bug at all: it was the
        downstream consequence of a player death that should not have happened, and that death came from
        `fn_012616` reading the action trip count at `record[+0x17]` instead of `record[+0x5c]` (docs/147).
        (c) selection arithmetic itself was already faithful: same LBAs (0x918e / 0x2d320 / 0x367aa / 0x9ddf),
        same track lengths (42/369/238/261 s), stage-anchor deltas +1900 / 0 / +109 ms.
      * DOCS: docs/106 (teardown fix, supersedes docs/96's LBA-offset hypothesis), docs/114 (selection
        equivalence), docs/135 (death → CONTINUE countdown → extra selection), docs/147 (the trip-count byte).
      * EVIDENCE: schedule oracle `scripts/rig/cd_schedule.py` — red "4 plays, 4 stops, 1 change with NO
        stop" -> green "4 plays, 5 stops, 0 changes with NO stop"; on the longer route 6 plays / 7 stops /
        0 un-stopped replacements. `NIGHT_DEATHTRACE` now reports deaths but **no player death**, matching the
        shipped side, and the extra idx12 selection disappears with it.
      * STILL OPEN inside this item: *audibility*. The shipped side never audibly plays track 11 on this drive
        (melodic peak-set IoU 0.19-0.40, replicated 0.380, docs/131) while the port plays it for 104 s. That is
        a content/timing divergence, not a teardown one.

- [x] Enemy/Player hurt/staggering motion is missing. Due to this sometimes infinite-punching.
      * ROOT CAUSE: the port gated the reaction-table lookup on `player && state == 0x97`, while the shipped
        block at guest 0x00014c6c-0x00014cb4 has one flat condition and an unconditional else-arm — so no
        entity could ever enter a reaction state; and `DAT_00051b60` (the reaction table, stride 4 in the hit
        code) was transcribed for 0x20 of its 0x400 bytes.
      * DOCS: docs/111 (table + unconditional arm), docs/137 (stride-4 decoding: code 1 -> 0x0b, 11 -> 0x15),
        docs/147 (the trip count that ends an action).
      * EVIDENCE: state census on `ep1_kill3` — player samples in `0x0b/0x0c` 0 -> 49 (shipped 47); after
        docs/147 the port census shows `0x0b x7, 0x0c x18` against shipped `0x0b x16, 0x0c x43`, and the
        hit-code-11 state `0x15` is gone from the player.

- [x] Defeating enemy doesn't gain any EXP.
      * ROOT CAUSE: `DAT_00053ea8` is `DAT_00053e9c + 0xc`, not a separate array. The port kept an unfilled
        array *and* added a spurious `+0x0c` at the death site, so the award read 0.
      * DOCS: docs/109 (fix), docs/125 §6b (the three writer sites: `+= victim[+0x32]` at 0x15453, the HUD ramp
        in `fn_0137c1`, the status-screen fold in `fn_038f3d`).
      * EVIDENCE: `NIGHT_ACTTRACE` EXP witnesses `adds=2 added=20` for two kills (shipped 10 per kill); record
        census shows the same `+0x2b` ladder on both sides (`0x0 / 0xa / 0x14`).

- [x] Enemy sometimes teleports.
      * ROOT CAUSE: not a port defect. Three oracle defects produced it: record addressing by summed
        `rec_bytes` instead of the dump's own offsets, 10 Hz vs 4 Hz cadence compared unnormalised, and
        appearances counted without identity linkage.
      * DOCS: docs/115 (the three rig fixes and the retraction).
      * EVIDENCE: corrected census — jumps 0.41 vs 0.43 per sample, unlinked appearances 5.9% vs 5.3%, hurt
        band 0.100 shipped vs 0.091 port.

- [x] Some SFXs are still missing like punching sound.
      * ROOT CAUSE: DS `0x53d08` is the sound-slot table one dword below the pool base `0x53d0c`; the port had
        invented `g_tab_53d08[101]` that nothing ever wrote, so `fn_04185e` always received null.
      * DOCS: docs/113 (alias + `g_sfx_plays`/`g_sfx_oob` witnesses), docs/129 §4 (`NIGHT_PLAYVOC`).
      * EVIDENCE: witness `played=74 outside-pool=0`; PCM witness 478 KB -> 1.14 MB concentrated in the fight
        windows; `NIGHT_PLAYVOC=7` dumps a shipped slot as VOC block type 1 length 0x1473 with peak 13568 and
        13355 non-zero samples.

- [x] Player/Enemy fallen state is almost missing. It barely happens.
      * ROOT CAUSE: the shipped data *does* contain fallen-producing reaction codes — the census in docs/156
        counts 71 in-band slots in episode 2 and 45 in episode 9, e.g. attacker type 2 / state `0x55` / slot 3
        holds code `0x19` -> victim state `0x62`. The reaction table read straight out of `NIGHT.EXE`
        (`0x51b60-0x7600 = 0x4a560`, 256 dwords) confirms codes `0x15..0x1f -> 0x66..0x5b` plus `0x3d/0x3e/0x42`
        -> `0x5c/0x5d/0x5e`, and that **no code maps to `0x99`, `0x70` or `0x71`**. Both direct stores of a
        fallen state in the whole shipped binary (`0x12926` in `fn_012616`, `0x14e07` in `fn_01441e`, both
        writing `0x66`) are gated on states `0x70` and `0x65`/`0x99`. The port transcribes both, including the
        easy-to-invert polarity at `0x1291c` (`store when pair[+0x30] != 1`) — `f.c:25993-26001`.
      * DOCS: docs/117, docs/118 §5-§9, docs/156 (supersedes docs/118's "exactly one fallen-class record").
      * EVIDENCE: **no divergence.** Runtime state population on the longest both-sides run (`/tmp/rig/g15`,
        1846 shipped / 2169 port samples): shipped `{0x33:72, 0x34:61, 0x35:59, 0x36:3}` and port
        `{0x33:117, 0x34:66, 0x35:70}`; `0x65`, `0x66`, `0x70`, `0x71` are zero on both sides. Neither side ever
        occupies the attacker states the fallen codes hang off (`0x55`, `0x7e`, `0x142`, `0x16b`, `0x1c7`,
        `0x1e2`), so the family is unexercised identically. The only fallen samples the rig ever produced were
        rig-written (`128060 ent 1 0x17 0x65`, docs/154 §2).
      * RESIDUAL (tracked as an upstream question, not a port defect): what raises an entity from the
        `0x01/0x02/0x33..0x35` band into `0x55`-and-above. The 36 register-sourced stores into `+0x17` (27
        functions; `fn_03272f` carries 4) are the candidates; this is the same open chain question as docs/110,
        docs/152 §4b and docs/155.

- [x] Hitting by enemy while kicking sometimes makes player stuck.
      * ROOT CAUSE: same reaction-table gate as item 2, plus the trip-count byte: with the counter never
        released the player stayed in the kicking action while a hit resolved against it. The lethal
        0x0b..0x14 band (docs/136's shipped rule at 0x00014cd2: a victim whose `word[+0x23]` is 0 hit by
        reaction code 0x0b..0x14 is marked dying regardless of hit points) then fired on the player.
      * DOCS: docs/111, docs/136, docs/137, docs/147.
      * EVIDENCE: the player's `+0x11` counter max 88 -> 69 (shipped 63), median 42 -> 31 (shipped 30); state
        `0x15` no longer appears in the player's census; `NIGHT_DEATHTRACE` shows no player death where the
        pre-fix build showed one at tick 7066 with hp 998.

## Residual open items after this ledger

1. **Fallen-state coverage** (item 6 above): needs a drive that produces the attacker state 0x65/0x99.
2. **Camera** (`DAT_000639dc`): shipped max 27, port 158 after docs/147 (298 before). The scroll clamp path
   (`fn_03cb38` / `fn_03cbd9`, the `g_dat_63354` clamp-bounds struct, and `fn_03ed6f`'s room parameter carrying
   `room[+0x32]`/`room[+0x36]`) is not yet instrumented on both sides.
3. **Room command counter**: shipped `DAT_00063e14` holds 67; the port wanders 61-67, and `fn_03e20f` has 14
   `rec[0]=0` stores where the shipped function body has 12 (docs/139).
4. **Who receives hit code 11** (`0x15`): measured on the longest both-sides run (`/tmp/rig/g15`, 300 s, 10 Hz,
   1846 shipped / 2169 port samples) — shipped puts *enemies* in `0x15` 43 times and the *player* never
   (0 samples); the port puts the player in `0x15` 67 times. So code 11 is a shipped behaviour and the defect
   is its target (docs/155). Answering it needs the shipped side's `byte[record + slot + 0x38]` for the same
   (attacker type, attacker state, slot) — i.e. a shipped-side `.act` container read, which the rig only has on
   the port side today (`actdump`), so this is a rig capability gap.
5. **Music audibility**: track 11 plays for 104 s in the port and is inaudible on the shipped side (docs/131).
