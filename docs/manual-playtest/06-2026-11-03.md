## Item D — stage 2: the vertical camera must follow the player, like the horizontal one

**Reported:** "camera y-pos should follow player like x-axis scroll. currently it scrolls to bottom
automatically."  The playtester re-tested the DOS original to confirm the expectation: *the original follows the
player vertically on stage 2 the way it follows horizontally, until the bottom is reached; after the bottom is
reached they could scroll right to reach the enemies.*

**What the shipped bytes say.**  The scroll cells are `DAT_000639dc` (horizontal, the viewport column) and
`DAT_000639e0` (vertical, the viewport row), both reached in the shipped as `[0x139dc]` / `[0x139e0]`.  A store
census over every modelled body (`scripts/audit/imm_scan.py`, 76 573 instructions in `0x10000-0x53000`) gives
every writer of each:

```
horizontal  DAT_639dc   8 stores, all in fn_03cc6b's scroll block
  0x3cb02 mov [0x139dc], eax        0x3cb14 mov [0x139dc], eax
  0x3cb84 add [0x139dc], 3          0x3cb98 mov [0x139dc], eax
  0x3cbb2 inc [0x139dc]             0x3cc22 sub [0x139dc], 3
  0x3cc30 mov [0x139dc], eax        0x3cc44 dec [0x139dc]

vertical    DAT_639e0   3 stores, in the same block
  0x3cb1f mov [0x139e0], eax
  0x3cd42 inc [0x139e0]             0x3cdfc inc [0x139e0]
```

Read the shapes: the horizontal cell has a fast arm (`add 3` / `sub 3`) and a slow arm (`inc` / `dec`) in both
directions.  The vertical cell has **only `inc`** — the shipped never decrements the scroll row there, it walks
it downward in one-row steps from two arms, plus one `mov` at 0x3cb1f.  That is exactly the behaviour the
playtester describes: the view follows the player downward until the room's bottom, and never back up.

**What the port does.**  The port models the horizontal arm (`fn_03cb38`, `f.c:14626-14646`: the `+3` / `right -
0x140` fast arms and the `+1` slow arm, the 0x3cb5b-0x3cbb2 block ✓) and it models the shipped's two vertical
`inc` arms inside `fn_03cc6b`:

```c
if ((int32_t)(((struct ua32 *)((c + 0xc)))->v) - 0xc8 > (int32_t)g_dat_639e0)
    g_dat_639e0++;                       /* f.c:9871  <- shipped 0x3cd42 */
...
if ((int32_t)(((struct ua32 *)((c + 0xc)))->v) - 0xc8 > (int32_t)g_dat_639e0)
    g_dat_639e0++;                       /* f.c:9886  <- shipped 0x3cdfc */
```

with the shipped's own tests (`0x3cd29-0x3cd42` and `0x3cde3-0x3cdfc`: `eax = [[ebp-4]+0x34c]`, `eax = [eax+0xc]`,
`sub eax, 0xc8`, `cmp eax, [0x139e0]`, `jle` skip ✓ so the step fires while the **next** node's `+0x0c` minus the
200-row screen still exceeds the current scroll row ✓ and it can only ever *increase* the row ✓ matching the
playtester's "follows down until the bottom, never back up") ✓

What is *not* modelled: `0x3cb1f mov [0x139e0], eax` (and its two horizontal neighbours `0x3cb02` / `0x3cb14`,
`grep -nE "0x3cb1f|0x3cb02|0x3cb14" port/src/f/f.c` returns nothing ✓) — the direct *placement* of the scroll
row, which lives in the block just before `fn_03cb38`.  A third writer is `fn_03cad3` (`f.c:9165-9167` ✓
`g_dat_639dc`/`g_dat_639e0`/`g_dat_639e4` from the room's setup block ✓ 0x03cad3 ✓), which is the only vertical
write the stage-2 sample basis ever observes.

**Measurement correction, in place.**  My first pass here claimed "the port has no per-frame writer of the
vertical scroll cell", from `grep -nE "g_dat_639e0 *[+-]?="` ✓ a pattern that cannot match `g_dat_639e0++` ✓ the
same failure class as the accessor-macro grep misses (docs/254 §3) and the `0x3b5c0`/`fn_0003b5c0` grep miss
(docs/252 §2).  The corrected census is `grep -nE "g_dat_639e0([+-]?=[+-]?|\+\+|--|\+=|-=)"` → three sites
(`f.c:9166`, `9871`, `9886`) ✓

**Diagnosis.**  The two `inc` arms exist in the port and the store census says the shipped has no decrement arm
for the vertical cell ✓ so "the camera never follows down" is not a missing store, it is the gate: the shipped
reads `[[ebp-4]+0x34c] + 0x0c` — the **next** node's `+0x0c` — while the port reads `c + 0xc`, and whether those
are the same record is exactly what changed in `444c2aa` (the room-record re-read fix) and what the stage-2
sample basis says they are not: `DAT_639e0` = 0 in all 1116 samples of `/tmp/rig/st2w` (episode-2 basis ✓ see
the basis note ✓) and all 1044 of
`/tmp/rig/s2full2` ✓ the arms never fire there ✓ Two things must be pinned from bytes before any change:
(1) `0x3cb1f mov [0x139e0], eax` and its `0x3cb02` / `0x3cb14` neighbours are unmodelled in the port — what
arm places the row directly, and from which record; (2) which record the port's `c` is at the moment the two
`inc` gates are evaluated on a stage-2 basis (the head node, the current node, or the next node ✓ the shipped
follows `+0x34c` ✓ and `444c2aa` changed how the loop's room pointer is held).  No new clamp, no invented
"follow the player" rule: only the shipped's own arms.

**Consequence for round 2's item B.**  The playtester's "only after the bottom did I reach enemies" is the
mechanism docs/312 §2 could not reach by scripting: the stage-2 boss record sits at `rx = 7096`
(`/tmp/rig/sg2`: `stgboss stage=2 rec=001ae224 sub=1 x=7096 y=166` ✓ **episode 2's** boss record, not episode
1's ✓) and is rejected by the spawn window
`room[0x00] <= rx <= room[0x08]` (`0x3e39f-0x3e50f`) in 223 of 223 dispatches while the port's view never moves
down.  Vertical follow is therefore upstream of item B's boss encounter ✓ it does not by itself settle item B,
but it removes the "the rig can never reach the boss" objection.

**Fix (planned, transcribed from those bytes).**  Rebuild `fn_03cc6b`'s scroll block against `0x3cb02-0x3cc44`
and `0x3cd20-0x3ce10`: keep the existing horizontal arms, add the vertical `mov` at 0x3cb1f and the two `inc`
arms at 0x3cd42 / 0x3cdfc with the tests those addresses actually perform — including whatever bottom limit
those arms compare against (the room record's vertical extent, `+0x2a/+0x2e/+0x32/+0x36`, read by the camera
policy `fn_03d4e4`).  No new clamp, no invented "follow the player" rule: only the shipped's own arms.

**Gate.**  Same drive on both sides of the change (`scripts/rig/drives/ep1_st2w.txt` with `--warp-episode 1
--warp-stage 2` — the playtester's ep1 stage 2 ✓ `--warp-episode 2` would be episode 2 ✓), skip-intro ON, pinned
env `NIGHT_SEED=13579 NIGHT_RIG_STEP_CALLS=665 NIGHT_RIG_FPS=60`: red = the `[vgate]` census showing
`inc_would_fire=0` on every visit and `DAT_639e0` never changing while the player descends (the episode-2 census
of `/tmp/rig/st2w` is on record but is the wrong map ✓ a fresh ep1 stage-2 run is owed ✓), green = the same drive
showing `inc_would_fire=1` and `DAT_639e0` climbing to the bottom limit, and the `SPAWNB` gate verdicts (`inx`)
for the episode-1 record moving from rejected to admitted as the view reaches its window.
Fixture: a `test_f1.c` case asserting `fn_03cc6b` performs the shipped's vertical arms (`0x3cd42`, `0x3cdfc`,
plus the unmodelled `0x3cb1f`) on a fixed input state.

## Item E — stage 3: one Enter press skips the whole boss dialogue

**Reported:** "ep1-stg3: Pressing enter key skips boss battle dialogue entirely. should skip line by line."
The playtester confirms the dialogue itself is the correct content and appears at the first entry to stage 3 ✓
only the key behaviour is wrong.

**Status: not yet localized.**  What is already known and narrows the search:

- The card/text key wait is `fn_00035dfc`, which accepts only Enter / CTRL / ALT / Space (docs/97), and the
  modelled port routine is `f.c` `fn_00035dfc` (docs/231 replaced a no-op stand-in).  Shift is *not* an advance
  key there, which is why `fn_038f3d` (whose exit set is Esc/LShift/RShift, `0x3920a-31`, docs/287) and the
  dialogue need different keys in a drive.
- The port's input pump runs on the order of a hundred `fn_0347e3` dispatches per presented frame (docs/274
  census: 122 posts against ~3 M pump entries), and the repeat credit `g_dat_62cd8` is only earned for a make
  arriving within ~4 dispatches of the original make (`0x3fdf2-0x3fe26`, docs/281).  A single held Enter
  therefore produces a burst of makes inside one frame's worth of logic, which is exactly the shape of "one
  press consumes every line".

**Plan.**  (1) Re-read the shipped dialogue loop's consumer: which routine pops one key post per line and what
it does with the rest of the queue (compare `fn_00035dfc`'s wait body with the shipped `0x35d5d-0x35e60` region
and the state cells it clears).  (2) Instrument line transitions and Enter posts with the same witness on both
sides of the change (counts only — posts and consumed-line transitions, never latency, per this goal's dump
rule).  (3) A drive that presses Enter once per line and counts lines consumed per press: red = lines advanced
> 1 per press on the current build, green = 1 line per press.

## Item F — stage 3's start effect (odd/even rows shifted horizontally) is missing

**Reported:** "Also missing screen animation (odd/even rows of screen crosses horizontally)" and, clarified:
*"It's after dialogue is finished, for effect of actual stage 3 start."*

**Status: not yet localized.**  The candidate machinery is known from the round-2 audit: the row-blit helper
`blt_rows` (0x040491) and its per-record caller `fn_03ce0b` (`0x3ce79-0x3d066`), which dispatches four arms
(B0..B3) over a record's top row `+0x04`, its own row count `+0x1a`, and a per-row source address; docs/311
fixed four places in that routine where a row delta was multiplied against a column field, and two arm tests
that had to be signed (`jge` at 0x3ce7c, `jle` at 0x3cf68).  A horizontal odd/even row offset is precisely what
a per-row source/destination delta produces, so the missing animation is most likely an arm of that family (or
a routine the stage-3 start calls between `fn_00035dfc` and the first room frame) whose arm never runs in the
port.  Current stage-2 evidence shows how little of that family the port exercises: `/tmp/rig/bl312e` (stage-2
warp basis) reports `blt_rows calls=268 ... arms B0=268 B1=0 B2=0 B3=0` — every call takes the plain arm, none
takes an offset arm ✓ while the stage-1 chain-advance basis `/tmp/rig/bl312f` reports `calls=936 ...
B0=576 B1=0 B2=103 B3=154` ✓ the offset arms do run in stage 1 and never in stage 2/3.

**Plan.**  (1) Find the writer in the shipped: census the stores/reads of the row-offset fields in the
`fn_03ce0b` family plus whatever the stage-3 tail calls after the dialogue (`fn_03d244 -> fn_038f3d(1)` at
`0x3d2ac`, then the room installer `fn_03cad3` at `0x3d2bb`), with `scripts/audit/branch_xrefs.py` /
`cfg_reach.py` to see which arm a stage-3 start reaches.  (2) Add a witness that counts per-row horizontal
offsets actually emitted (row → column delta), armed on a stage-3 basis drive.  (3) Red = 0 offset rows emitted
on a stage-3 basis (the `/tmp/rig/bl312e`-style census is already that shape ✓), green = offsets matching the
shipped's arithmetic for the same records.

## Item G — a health upgrade gains more HP than one step should

**Reported:** "Health upgrade gains too much health, I think single upgrade gives full level of unlock",
clarified: *"HP Upgrade adds additional HP bar (it's stacked by color like red, yellow...). Single upgrade only
should step 2 bars but it gained more."*

**What the port does today** (`fn_038f3d`, the level-up screen, the tail that commits a purchase, shipped
`0x39a56-0x39b10`):

```c
if ((int32_t)P[0x27] != sel[0]) {              /* 0x00039a56-0x00039ab0 */
    g_dat_62a98 = keys[(uint32_t)sel[0]];      /* (&DAT_00062aa0)[sel] */
    g_dat_62a9c = keys[5u + (uint32_t)sel[0]]; /* (&DAT_00062ab4)[sel] */
    P[0x27] = (uint8_t)sel[0];
}
P[0x28] = (uint8_t)sel[1];                     /* 0x00039ab5-bf */
if ((int32_t)P[0x26] != sel[2]) { P[0x26] = ...; g_dat_62a8c = acts[sel[2]] - hb; }
P[0x25] = (uint8_t)sel[3];                     /* 0x00039b41-… */
```

Row 0 (health) commits by storing the *count* `sel[0]` into the player record's `+0x27` and re-deriving a pair
of scalars from two five-entry tables `DAT_00062aa0[sel]` and `DAT_00062ab4[sel]` ✓ the pair is the natural
place where a "how much HP, and how many stacked bars" pair would live.  The bar drawing in the same routine
(`0x39848-0x399a2`) picks a bar image with `idx = gbase[i] + n - 1` where `n` is the row's own count plus the
cursor preview (`n = shown + 1` only while the cursor sits on that row ✓ docs/228 ✓).

**Status: not yet gated.**  Two things must be read out of the bytes before any change: the actual values in
`DAT_00062aa0` / `DAT_00062ab4` (five entries each ✓ their contents are the shipped's per-step HP amounts), and
which record field the stacked bars are counted from (`+0x27` is the upgrade level ✓ the HP itself is
`+0x29` ✓ with the damage pool at `+0x56` and the pending term at `+0x23` per docs/297/docs/312's field map ✓).
The candidate defects are (a) the port's `sel[0]` climbing by more than one per purchase, (b) the table index
used for the bar stack being the level rather than the bar count, or (c) the bar count derived from an HP delta
instead of the purchased step count.

**Gate.**  A witness that logs, per purchase, `sel[0]` before/after and the pair `g_dat_62a98 / g_dat_62a9c`
before/after, driven by a drive that presses Enter exactly once per purchase on a stage-3 basis (arm-2 pokes
+ Esc to leave the menu ✓ docs/287).  Red = the measured step per purchase on the current build; green = one
purchase advances `sel[0]` by 1 and the HP pair by exactly the shipped's table row.  Cross-check static side:
dump `DAT_00062aa0` / `DAT_00062ab4` from the disc image and print both tables in the fixture so the expected
step is data, not a guess.

## Item H — after clearing stage 3: one picture, then the upgrade menu, screen glitched until the menu is left

**Reported:** "After ep1-stg3 single frame of image shown then enters upgrade menu again. but screen is
glitched until exit the menu."  Added to the goal as task-12 (it was missing from the round-4 objective text).

**The shipped's stage-clear sequence, with offsets.**  Only request 3 clears a stage (`0x3abca-0x3abdd`), so the
tail runs from `fn_03af18`: the picture/card pair driven by `g_tab_52f2c[episode]` (`f.c:28272-28290`, witnessed
as `slide: card n/N wait` in `/tmp/rig/k312`), the resource reload `fn_037b03(0)` called from `fn_0374ad` at
`0x37615`, the room-chain advance `fn_03d244` (`0x3d286-0x3d2a2`, terminator `DAT_63354 = DAT_00063350`), which
**calls the upgrade menu `fn_038f3d(1)` at `0x3d2ac`** and only *then* the room-setup installer `fn_03cad3` at
`0x3d2bb` (the routine that sets `DAT_639dc`, `DAT_639e0`, `DAT_639e4` from the new room record ✓ `f.c:9165-9167` ✓).
The tail also tears entities and heap blocks down (`f.c:28189` records the shipped's entity-remove + heap-free
pair around `0x3b52b`).

**Why that shape produces the reported symptom.**  `fn_038f3d` composites itself from the heap: each frame it
copies its own background PCX into the scratch plane (`mem_copy(video_map(g_dat_633b0), hb + o_pcx, 0xfa00)` at
`0x39762-67` ✓ `f.c:26421` ✓), draws the upgrade bars out of the same heap area (`0x39848-0x399a2`, bar image
selected by `gbase[i] + n - 1`), then pushes the scratch plane to the screen
(`mem_copy(video_map(0xa0000), video_map(g_dat_633b0), 0xfa00)` at `0x399ff-0x3a0f` ✓ `f.c:26494` ✓).  So a
*persistently* glitched menu means the heap content the menu reads is already stale or freed while the menu is
drawing — the menu is faithfully drawing garbage, which is why the corruption lasts exactly as long as the menu
is open ✓ the report's own phrasing ✓ — and the single held picture is the last slide card before that point.

Two candidate defects, both testable against bytes rather than by eye:
1. **order**: the port runs the tail's teardown before `fn_038f3d(1)` where the shipped runs it after (or vice
   versa) — check the call order around `0x3d2ac` / `0x3d2bb` against the port's `fn_03d244` and `fn_03af18` tail
   (`f.c:28240-28380`);
2. **the freed range**: the tail's heap free releases the block that holds the menu's background/row art
   (`hb + o_pcx`, `lvl[14] + so[idx]`), so the menu reads a released block.

**Gate planned.**  A stage-3-clear basis drive (arm-2 pokes + Esc to leave the menu ✓ docs/287 ✓ skip-intro
stated, and skip-intro is *off* on any run that measures the card/picture phase ✓ docs/309 ✓) with
`NIGHT_ROOMDBG=1` (the `-> fn_038f3d(1) level-up screen entry` / `returned` markers already in `/tmp/rig/st2g`:
9 entries ✓ and `/tmp/rig/l312e`: 6 entries, 5 returns ✓), plus a witness naming which heap block supplies
`o_pcx` / `lvl[14]` at menu entry and whether it is live at that moment, plus the `NIGHT_BLITDBG` arm census at
menu entry.  Red = the menu's source block reported freed/stale (or the wrong order) on the current build;
green = live source block and the shipped's order, on the same drive.
