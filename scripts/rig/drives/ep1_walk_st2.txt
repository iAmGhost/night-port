# Stage-walk drive (docs/313 §2, §6): reach EPISODE 1's second room node ("stage 2") the way a player does,
# then hold Down at the bottom.  No warp flag.
#
# Why this exists: the previous "stage 2" bases were wrong twice over.  `--warp-episode 2` loads episode 2 (a
# different map, docs/312 0a) and `--warp-stage 2` installs a node without re-loading that stage's background
# (docs/313 §1).  Neither can carry a camera or sprite claim.
#
# "Episode 1, stage 2" is the second node of episode 1's own chain: DAT_00063370 stays 1, and one call of
# fn_03d244 (which swaps DAT_63354 to node+0x34c, or to the terminator g_dat_63350 at the last node,
# 0x3d286-0x3d2a2) is one stage.  The harness counts those calls (f_rig_chain_advances).  Each advance opens
# the level-up screen (fn_038f3d(1) at 0x3d2ac), which leaves only on Esc/LShift/RShift (0x3920a-31) -- so the
# drive waits for it (`wait state menu-open`), runs the `menu` macro, and continues.  The macro presses and
# HOLDS (800 ms) rather than posting down+up in the same pass: same-instant pairs hide the latch between two
# reads of DAT_00063e89 and the screen never left in 100 posts (/tmp/rig/w313f), held keys left it in 4
# (/tmp/rig/w313g) -- docs/313 §6.
#
# Requests are arm 2 (DAT_6336c = 2).  fn_03a829 checks the request only at the loop bottom (0x3abc0-0x3accd)
# and its per-room prologue clears the cell twice (0x3a95a-0x3a984, 0x3a9e1-0x3aa04), so a poke usually dies
# in the prologue: the drive repeats it and then waits for an actual advance instead of assuming one.  Right is
# held while the requests run, as in play.
#
# Note on `wait state` lines: their deadline is the line's own time (port/src/app/main.c PT_WAIT_STATE), so the
# deadlines below are deliberately far apart and every later event rebase shifts left when the wait hits.
#
# Measurement window for item D: after the menu closes, Right is released (so the exit rect cannot fire again
# and pollute the window), Down is held 30 s, then Right is held.  Witnesses: [vgate] (the fn_03cc6b gate and
# its inc), [yclamp] (fn_01586b's mn/mx band and the d it passes), DAT_639e0/639dc/639e4, player_recs.jsonl.

# Rebase note (docs/314): a `wait state` line shifts every LATER line earlier by the slip, so the `menu` macro
# must sit immediately after the anchor line (/tmp/rig/w314c: scheduled 32 s out it became current only 34 s
# after the advance and 14090 of 16000 frames were menu-owned).  `menu` is also sprinkled through the request
# phase: each advance opens fn_038f3d, an unhandled one swallows the rest of the run (14042 of 16000 in
# /tmp/rig/w314f), and the macro exits at once when no screen is open.  A DOWN window must not sit inside a
# menu: /tmp/rig/w314f measured `walking-body calls 149, player DOWN fn_01586b calls 0`.

# Why Right is released on the anchor line (docs/314): the anchor pulls every later line earlier, so `key right up`
# fires the instant the advance lands.  Leaving Right held lets a leftover request land in the NEW room's exit
# rect too -- /tmp/rig/w314i advanced twice back to back and the clean stage-2 window was 19 samples of 5 Hz.
# Arm 2 (0x0003ac2a) only advances while the player stands in the exit rect the room publishes, so stopping the
# walk is what keeps one stage in the measurement window.
